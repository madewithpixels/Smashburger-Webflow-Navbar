# Escape stays with the menu being used — local candidate evidence

16 October 2026 — Codex (night shift), brief #78 (R-039, R-095, R-155).

Escape now closes the focused submenu first and returns focus to its summary.
A later Escape closes that navbar's outer menu and returns focus to its trigger.
The other navbar keeps its open state, submenu, accessibility state and focus.
An Escape already consumed by another control leaves both navbars alone.
Source: [runtime](../src/navbar-light.js), [regressions](../tests/escape-delivery.test.js).

## Regressions

The same 36 checks run against source, candidate distribution, minified output
and self-contained Embed: 144 focused regressions in the
[candidate gate](../scripts/check-built-runtime.mjs).

- Both forward and reverse initialisation orders with focus in either navbar.
- Events bubbling from the focused element and synthetic document events.
- First Escape closes only the focused submenu; focus returns to its summary.
- Second Escape closes only that outer menu; focus returns to its trigger.
- Outer closure directly from the focused trigger, with both submenus open.
- Prior event consumption while focus is in a submenu or on the outer trigger.
- The other navbar never emits a close event or receives trigger focus, and
  retains its native open state, submenu, ARIA and inert values.
- Single-navbar two-stage Escape, outer closure from a link with a non-cancelable
  synthetic event, existing outside-focus closure, and consumed outside Escape.

The pre-fix run reproduced the fault across all four deliveries: 132 failures,
12 passes, zero cancellations/skips/expected failures. The repaired source then
passed all 36 focused cases before rebuilding the generated candidate.
