# Focus before closing — local candidate evidence

16 October 2026 — Codex (night shift), brief #77 (R-038, R-040, R-155).

The unreleased candidate now returns focus to the menu trigger when closing
would leave it inside the hidden panel. Focus already on an outside control
stays there. The existing explicit `focusTrigger: true` option still requests
trigger focus. This is local DOM evidence, with no browser or assistive-technology
verification. Historical Acceptance is unchanged; this repair awaits Michael's review.

## Regressions and results

[Focused tests](../tests/close-focus-delivery.test.js) are included in the
[candidate test gate](../scripts/check-built-runtime.mjs).
The same 30 checks run against source, candidate distribution, minified output
and self-contained Embed: **120 focused checks**.

- Public close, explicit false focus option and public toggle.
- Native closure with focus inside the panel and already outside it.
- Enabled direct-link and nested-link descendant clicks.
- Enabled outside closing with focus still inside or already on the clicked control.
- Preservation of outside focus for public/link closing and during the closing wait.
- Preservation of the existing explicit trigger-focus option.
- Disabled link/outside closing retains focus, open state and panel accessibility.
- Every case uses 0ms and 45ms closing durations and a separate 0ms opening duration.

The tests record focus synchronously before native close, each closing/closed
state write, `aria-hidden` and inertness. They also assert focus at the close
event and after completion, plus the configured closing timer. This proves
ordering in the simulated DOM, rather than checking only the final active element.
An externally changed native open property necessarily changes before the toggle
handler runs; its check establishes focus safety before the runtime's own hiding
writes, not before an external caller's change or a browser's native rendering.
